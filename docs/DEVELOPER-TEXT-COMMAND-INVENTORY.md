## Boundary / context

`parseHumanCommand(line, ctx)` is explicitly an *agent text-line adapter*, legacy-named, not hosted human PLAY; the S0 spec says NON-CANONICAL DEV TOOLING and production agents use structured observations/actions (`workers/noema/src/actions.ts:1031-1048`; Specs `docs/MUD-NATIVE-INTERACTION-TASKS.md:9-16`). Context fields are `entities`, `players`, `selfId`, `openTrades`, `exits`, `hintCommands`; `openTrades` is declared but never read by this parser (`workers/noema/src/actions.ts:1036-1046,1036-2179`). Case-insensitive phrase regexes and lowercased first verb; leading/trailing whitespace trimmed; most token commands read only the operands they need and silently ignore surplus tokens (`workers/noema/src/actions.ts:1047-1050,1252-1254`). Empty input gives `Type a command, or use an action below.` **without code** (`workers/noema/src/actions.ts:1047-1048`).

Text-target resolution: when nonempty `ctx.entities` exists, entity commands resolve visible **labels only**, exact normalized label before partial/word-overlap, never guessed internal entity_id. No match → `NOT_FOUND` (`Choose something visible.` for empty, else `You do not see “X” here.`); multiple exact/partial matches → `AMBIGUOUS_TARGET`, numbered `Which one?` list, capped at nine, optional `Be more specific to reach the others.`; absent/empty entities → raw target is accepted into the canonical action, without parser-level visibility validation (`workers/noema/src/actions.ts:632-641,766-807,1292-1308,2201-2207`). Player resolver excludes self; exact full/suffix id (unique) then exact handle/player-id stem then partial handle; shared exact handle or partial gives bounded `AMBIGUOUS_TARGET`; no match gives `NOT_FOUND: No addressable Player “X”.`; a duplicated exact ID match has no explicit ambiguity branch and continues into handle/partial matching. If either `players` or `selfId` missing, most caller branches pass raw player token through. This is *not* the proposed #795 MESSAGE-specific resolver (`workers/noema/src/actions.ts:809-842,1055-1069`).

Movement alias map is **only** `n/north`, `s/south`, `e/east`, `w/west`; unrecognized operand after `move/go/walk` is still a successful MOVE parse with raw lowercase direction; bare unknown word is not MOVE. Neither the parser nor `canonicalizeDirection` checks that an exit exists; admission does (`workers/noema/src/actions.ts:1003-1019,1274-1291`). `stripInspectNoun` repeatedly strips `at/the/a/an` with following space; it is not noun discovery (`workers/noema/src/actions.ts:1021-1029`).

## Admission-only interpretation (not aliases of `parseHumanCommand`)

Developer admission selects `arguments.line` over `command`; alias commands are intercepted before parse, expansion and macro split happen first; direct service `ask/talk/use/consult/service` handling can return a non-mutating desk observation **without** entering the text parser. `parseHumanCommand` itself treats those words as unknown absent this interception. Macro `do` and semicolon are not parser verbs (`workers/noema/src/world-actions.ts:2021-2110`; `workers/noema/src/command-aliases.ts:44-48,116-127`). `alias [list]`, `alias [set] <name> <expansion>` (also `alias <name> <expansion>`), `alias rm/remove/unset <name>` mutate player preference map, not world truth; rejected reserved names and malformed names when setting an alias, malformed commands, and the 16-alias ceiling yield text in an **ok admission result**, not `ParseResult` errors. Setting an alias lowercases its name and requires a letter followed by up to 23 alnum/_/- characters; removal does not validate the name (`alias rm $$$` is accepted as a removal request). reserved built-in subset includes `look/l`, `message/msg/tell/say`, `trade`, `do`, `talk` etc., but is *not* an exhaustive reservation of the accepted text verbs. Recursive expansion depth >4 → admission `ALIAS_DEPTH` (`Alias expansion is too deep.`). Macro max five nonempty semicolon steps (`Macros are at most 5 steps.`), `do` stripped, inner `do` or nested macro → admission `MACRO_REJECTED` (`Macros cannot nest.`); pinned player tempo refuses multi-step macro (`Pinned player-tempo admits one action per cycle.`). Steps execute sequentially, stop at failure (`workers/noema/src/command-aliases.ts:3-127`; `workers/noema/src/world-actions.ts:2033-2080`).

Routing is **not all text**: developer + `arguments.line` (or expanded line) → text parser; otherwise structured normalizer. A failed non-protocol/spaced `envl.command` may fall back to text, but protocol verbs are protected. Clarification stores bounded choices with observation fingerprint/session, numeric or unique label/prefix pick, invalidates on next non-pick or changed observation/session. A picked MESSAGE requires rewriting its private body rather than replaying it; parser alone does not retain clarification state. `HELP` is converted to successful help observation; missing MOVE direction gets special failedMove path; some failed MESSAGE/HARVEST/REPAIR errors are reworded/redacted at admission (`workers/noema/src/actions.ts:2257-2273`; `workers/noema/src/world-actions.ts:2026-2032,2164-2320`).

**Separate structured path:** `normalizeStructuredCommand` uppercases `command`, accepts `LOOK/WAIT/OBSERVE/ENTER_WORLD/JOIN` (`JOIN→ENTER_WORLD`), `LEAVE_WORLD`, `MOVE` (direction/exit_id/target_id), `INSPECT` (entity_id/target_id/target), `MESSAGE` (surface BOARD/SHOUT/NOTICE/CHANNEL/TRADE_NOTICE or direct recipient), `TRADE`, `COMMIT` operations, `BUILD` operations, direct `REPAIR/HARVEST`, and direct operation aliases (`CONTEST_*`, `ATTEST`, `AGREEMENT_*`, `ACCESS_POLICY`, `FOCUS`, `ORG_*`, `RECONSTRUCT*`). This is **not** a text-alias list. Structured MOVE/INSPECT missing target → `INVALID_REQUEST`; MESSAGE surfaces require text, CHANNEL additionally org_id; direct requires recipient plus text or parent_claim_id and validates signal; TRADE phase defaults propose and carries optional argument fields, leaving several validations to admission (`workers/noema/src/actions.ts:2276-2398`). COMMIT operation-specific required fields/errors and their direct aliases are enumerated in `workers/noema/src/actions.ts:2399-2910,3025-3103`; BUILD operations and required operands in `:2933-3023`; direct REPAIR/HARVEST in `:2911-2932`. Structured unknown → `UNKNOWN_COMMAND`; forbidden contest verbs → `VERB_FORBIDDEN`. Do not infer a text spelling from a COMMIT operation. `parsePlayCommand` is another adapter that calls `parseHumanCommand` with entities only and renders HELP through `helpText` (`workers/noema/src/play-ui.ts:579-603`).

## T0.2 contract and #795 boundary

**Branch-local T0.2 implementation at `922f98ad33723fa42968bf33323930ce88984249`, built on merged base `08190b370f985fcca6e29d291ef500bfe3d73abd` (not present in that base; supersedes the historical inventory description only for this branch):** Shared `ParseResult` remains `{ok:true, action, display}` or `{ok:false,error,code?,choices?,reason?}`. Only `parseHumanCommand` returns `HumanParseResult`, adding transient `sourceInput` equal to the exact string passed to that invocation, including empty input, case and whitespace. An alias or macro passes its expanded step, not its outer envelope. `normalizeStructuredCommand` never fabricates a source. `classifyParseResult(r)` is a separate, after-the-fact classifier: success → `resolved`, `AMBIGUOUS_TARGET` → `ambiguous`, `UNKNOWN_COMMAND/NOT_IMPLEMENTED/HELP/SERVICE/VERB_FORBIDDEN/CLASS_FORBIDDEN` → `unsupported`, all other failures (including no-code syntax and `NOT_FOUND`) → `invalid`. It does not replace stable `ok`, canonical action or admission outcome (HELP becomes successful help at admission). `parsePlayCommand` and reducer project explicit fields and discard source; it is not a retained world, pending, event, response or log field. Successful canonical message text retains its existing delivery semantics; rejected private message text must not persist. Evidence is local only, not hosted acceptance.

**Historical #795 note (no longer current):** #795 was OPEN at review on the older inventory pin (proposed head `a529f02c4c75e65911e64ecb5755dd8154d03f6a`); its recipient changes are included in current base `08190b3`. Its developer-text direct-MESSAGE-only policy (`message`/`msg`/`tell`/`say to`) prioritizes literal full `player.` IDs, then literal handles with hyphen/underscore/space distinct (a resolver policy: the direct-MESSAGE text grammar captures one recipient token, so a space-containing handle cannot be entered as a single recipient through that grammar), then punctuation-preserving partial handle substring among co-located Players; duplicate literal handles use co-located holders only. Unresolved names pass to admission's uniform `FORBIDDEN` refusal, and structured MESSAGE remains unchanged. It is **not** this base's `resolvePlayerTarget`, nor a general policy for all Player-naming verbs: report/pass/share/repeat remain tracked by OPEN #796 and observation roster by OPEN #793. Historical evidence: #795 review head and the older inventory's source spans; current merged behavior is on `08190b3` and its line spans have shifted.
